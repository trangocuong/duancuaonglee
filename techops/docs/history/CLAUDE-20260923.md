- Module 시트는 같은 내용을 한국어 표(4~25행)와 베트남어 표(36~57행)로 1:1 나란히 담고 있어서(통역이 이미 둘 다 작성해둠), `작업내용`/`비고`의 `value`(한국어)·`value_vi`(베트남어)를 둘 다 사람이 쓴 원문으로 채움 — AI 번역을 거치지 않음. `value_en`은 비워뒀고 화면에서 영어로 볼 때만 캐시(`tech_translation_cache`)를 통해 그때그때 번역됨. SSD 시트는 애초에 한 셀 안에 한국어/베트남어 라벨이 섞인 한 덩어리 텍스트라(`평가 / Tên đánh giá : ...`) 언어를 분리하지 않고 원문 그대로 `value` 한 칸에만 넣었음.
- `제품`/`진행중인 공정`/`업무구분`/`소속`(EAV 필드)은 이번 적재에서 비워둠 — 원본 엑셀에 해당 값이 깔끔하게 분리되어 있지 않아 억지로 채우면 오분류 위험이 더 크다고 판단함. 대신 `tech_daily_item.category`(항목 등록 시 1회 자유 텍스트, 예: SSD는 `Evaluation`/`Analysis`/`Equipment`, Module은 원본 그대로 `고객 평가/ PGM/ EVAL` 등)에 원문 분류를 넣어뒀고, `/daily-reports`의 분류 열은 `u.category`를 `업무구분` EAV 값보다 우선 표시하므로 화면에는 정상적으로 나타남.
- `파트넘버`/`랏넘버`/`수량`은 SSD만 채움(원본에 Part ID/Lot No/수량이 별도로 있었음). Module은 원본 서식 자체가 로트 추적형이 아니라 서술형이라 대부분 비워둠 — 필요하면 `작업내용` 원문에서 확인.

### 언제 브랜치를 쓸지 (2026-09-03, Claude·Codex 합의)

문서 수정이나 서로 겹치지 않는 작은 변경은 최신 `main`에서 바로 작업해도 됩니다. 다만 아래에 해당하면 짧게 끝내는 임시 브랜치를 권장합니다: `worker.js` 변경, `schema.sql`/DB 마이그레이션, `wrangler.toml`, 인증·보안·데이터 무결성 관련 변경, 여러 파일에 걸친 기능 변경, 운영 장애 가능성이 있는 변경.

- **PR 리뷰는 필수 단계가 아닙니다** — 담당 에이전트가 브랜치에서 테스트까지 마친 뒤 스스로 `main`에 병합합니다.
- **"작게 나눠 자주 커밋"은 브랜치 안에서만 적용합니다.** `main` push는 곧 Cloudflare 배포이므로, 검증되지 않은 조각을 여러 번 push하면 그때마다 운영에 반영됩니다 — 브랜치에는 자주 commit/push하되, `main`에는 검증된 단위로 한 번에 병합합니다. `main`에는 force push하지 않습니다.
- **동시 작업 신호는 실시간 잠금 대신 브랜치 이름으로 표시합니다** (예: `claude/worker-translation-fix`, `codex/worker-report-filter`). 위 목록에 해당하는 작업을 시작하기 전에 `git branch -r`로 열려 있는 `claude/*`/`codex/*` 브랜치가 있는지, 최근 커밋이 같은 영역을 건드리고 있는지 확인합니다. 겹치면 바로 수정하지 말고 범위를 나누거나 사용자에게 중재를 요청합니다. 작업이 끝나면 병합 후 브랜치를 삭제해 점유를 해제합니다.
- **`main` 병합 직전에는 낙관적 동시성 검사를 합니다**: `git fetch origin` → 작업 기준 이후 `origin/main`이 바뀌었으면 최신 `main`을 반영 → 충돌 해결 후 테스트 재실행 → push. push가 non-fast-forward로 거부되면 강제로 밀어붙이지 말고 다시 동기화합니다 (git의 거부 자체가 마지막 안전장치).
- `main`에 병합한 사람이 그 결과로 나온 Cloudflare 배포 확인까지 책임집니다.
- 이 문서에는 장기 상태와 운영 이력만 기록하고, "지금 이 브랜치는 누가 쓰는 중" 같은 일시적 점유 정보는 넣지 않습니다(브랜치 자체가 그 신호입니다).
- 장기적으로 `worker.js`를 기능별로 나누면 병렬 작업이 쉬워지지만, 이 프로젝트는 "빌드 없는 단일 파일" 설계를 의도적으로 유지하고 있어서 지금은 위 절충안으로 운영하는 쪽이 낫다고 판단함.

## 공유된 운영상 위험 (실제 장애 이력 포함)

1. **`wrangler.toml`은 선언적으로 배포됩니다.** Cloudflare 대시보드에서 바인딩(D1 등)이나 변수를 수동으로 추가해도 `wrangler.toml`에 없으면 다음 Git 배포 때 사라집니다. 바인딩을 추가/변경할 때는 항상 `wrangler.toml`도 같이 커밋할 것. (2026-08-28: 이걸 놓쳐서 D1 바인딩이 날아가 전체 서비스가 Error 1101로 죽은 적 있음.)
2. **`wrangler.toml`의 `name` 값을 임의로 바꾸지 말 것** — 바꾸면 Git 자동배포가 새 이름의 별도 Worker를 만들어버릴 수 있음.
3. 시크릿(`SETUP_TOKEN`, `RESEND_API_KEY`)은 **wrangler.toml에 절대 넣지 말 것** — 대시보드 또는 `wrangler secret put`으로만 관리.
4. **DB에 저장되는 `status`(검토중/조치중/완료/보류), `priority`(상/중/하) 값은 항상 한국어 원본 그대로 유지.** 스키마 CHECK 제약과 CSS 클래스명(`.b-검토중` 등)이 이 문자열에 의존함. 화면에 보여줄 때만 `worker.js`의 `I18N.<lang>.statusLabels` / `priorityLabels`로 번역. 새 화면 문구를 추가할 때는 `I18N` 객체(ko/en/vi 3개 언어 키)에 반드시 같이 추가할 것 — 하나라도 빠지면 해당 언어에서 `undefined`가 노출됨.
5. **기존 테이블에 컬럼을 추가할 때(`ALTER TABLE ... ADD COLUMN`)는 기존 행의 기본값/백필을 반드시 같이 처리할 것.** (예: `email_verified_at` 컬럼 추가 시 기존 계정을 전부 인증완료로 UPDATE하지 않았다면 관리자 로그인이 즉시 끊겼을 것.)
6. 큰 파일(`worker.js`)을 브라우저에서 GitHub에 반영할 때는 웹 코드 에디터에 직접 타이핑하지 말 것 — Monaco/CodeMirror류 에디터의 자동완성/자동들여쓰기로 코드가 깨질 위험이 있음. GitHub의 "Upload files"(드래그앤드롭/파일선택, `/upload/main`)로 로컬에서 완성한 파일을 올릴 것. (로컬 git 환경에서는 이 문제 자체가 없음 — 그냥 커밋하면 됨.)
7. **베트남어(또는 다른 언어) 화면이 이상하게 보인다는 제보를 받으면, 먼저 브라우저 자동 번역(Chrome/Edge의 "이 페이지 번역") 여부부터 의심할 것.** (2026-08-30 실제 사례: 베트남어로 전환했더니 "작품"/"픽리스트"/"등록부" 같은 이상한 한국어가 보인다는 제보가 있었으나, 서버가 실제로 내려주는 HTML은 `curl`로 확인 결과 정상적인 베트남어(`<html lang="vi">`, `Đăng nhập · Quản Lý...`)였음 — 브라우저가 사용자의 시스템 언어(한국어)에 맞춰 베트남어 페이지를 자동 재번역하면서 생긴 현상이었음. 이미 앱 자체가 ko/en/vi 3개 언어를 완전히 지원하므로 `layout()`의 `<html>` 태그에 `translate="no"` + `<meta name="google" content="notranslate">`를 넣어 브라우저 자동 번역을 원천 차단해둠. 언어 관련 버그 제보가 오면 코드(I18N 객체)를 고치기 전에 `curl`로 실제 서버 응답부터 확인할 것.
   - 다만 이건 "고정 UI 문구"에 한정된 얘기고, `tech_daily_field.label`처럼 **관리자가 직접 입력한 이름**은 애초에 번역 자체가 안 되어 있는 게 정상이었음(브라우저 자동 번역과는 별개의, 실제로 존재했던 기능 공백). 이 경우는 `label_en`/`label_vi` 컬럼을 추가해서 관리자가 직접 번역을 입력하게 하는 걸로 해결함(2026-08-31, 위 "필드 이름 다국어" 항목 참고) — 브라우저 번역 의심과 실제 미번역 데이터 문제를 혼동하지 말 것.
8. **네비게이션은 왼쪽 사이드바(2026-08-31, 기존 상단 가로 메뉴에서 변경)**: `layout({ title, user, lang, body, activeNav })`의 `activeNav`("daily"/"tasks"/"full-analysis"/"master-data"/"settings"/"users")로 사이드바에서 어떤 메뉴를 강조할지 정함 — 로그인 후 보이는 페이지 핸들러는 `layout()` 호출 시 꼭 넣어줄 것(빠뜨려도 에러는 안 나고 그냥 강조 표시만 안 됨). 메뉴는 일일업무 보고=`/daily-reports`, 평가업무 관리=`/tasks`, 전수분석 현황보고=`/full-analysis-reports`, 기준정보 관리현황=`/master-data-status`, 설정=`/daily-fields`(관리자 전용), 회원 승인 관리=`/admin/users`(관리자 전용) 순서다. `/daily-items`(입력)와 `/daily-reports`(조회)는 사이드바에서는 "일일업무 보고" 하나로 합쳐져 있고, 대신 두 페이지 상단에 `dailyWorkSubtabs(L, "input"|"report")`로 작은 탭을 붙여 서로 오가게 해뒀음 — 이 두 페이지 중 하나만 있고 다른 하나로 가는 링크가 없는 상태로 고치면 안 됨. 언어 선택·접속자 정보·로그아웃은 사이드바가 아니라 모든 페이지 오른쪽 위의 `.page-tools`에 같은 14px 크기로 가로 배치한다.

## DB 테이블 (schema.sql)

인증/가입: `techops_users`(email_verified_at 포함), `techops_sessions`, `techops_login_attempts`, `techops_password_resets`, `techops_email_verifications`
업무관리: `tech_task`, `tech_update`, `tech_report_log`, `tech_daily_report`, `tech_daily_item`, `tech_daily_update`, `tech_daily_field`, `tech_daily_field_option`, `tech_daily_update_value`

### `tech_daily_item` / `tech_daily_update` + 동적 필드(`tech_daily_field*`) (2026-08-30, SSD/Module 입력 화면의 실제 저장소)

엑셀에서 매일 같은 항목을 복사해서 값만 바꿔 쓰던 방식을 대체하는 구조. `tech_task`/`tech_update`와 동일한 패턴이되, **입력 항목 자체를 관리자가 코드 수정 없이 추가/삭제할 수 있도록 EAV(Entity-Attribute-Value)로 설계**했다:

- `tech_daily_item` — 항목을 **한 번만** 등록 (part/category/title/owner). `closed_at`이 NULL이 아니면 종료된 항목.
- `tech_daily_field` — 일일보고 업데이트 폼에 나타나는 입력 필드 정의(label/input_type/sort_order). `input_type`은 `text`/`textarea`/`select` 중 하나. **관리자가 `/daily-fields`에서 직접 추가/삭제/수정** — 코드 배포 없이 폼 구성이 바뀜.
- **순서 변경(2026-08-31 추가)**: `/daily-fields` 목록의 ▲▼ 버튼(`POST /daily-fields/:id/move`)이 인접한 필드와 `sort_order` 값을 맞바꿔서 순서를 옮김. 이 순서가 실제 업데이트 입력 폼(`pageDailyItemDetail`의 `fieldInputs`)이 필드를 나열하는 순서와 완전히 같음 — 두 곳이 똑같이 `loadDailyFields()`(= `ORDER BY sort_order, id`)를 쓰기 때문에 순서를 바꾸면 입력 폼에 즉시 반영됨. 새 필드는 항상 `max(sort_order)+10`으로 맨 뒤에 붙는다.
- **필드 이름 다국어(2026-08-31 추가)**: `label`(한국어, 필수) 외에 `label_en`/`label_vi`(둘 다 선택)를 가짐. 화면에 필드 이름을 보여줄 땐 `worker.js`의 `resolveFieldLabel(field, lang)`을 통해서만 접근할 것 — `field.label`을 직접 쓰면 화면 언어가 en/vi여도 한국어가 그대로 노출됨. en/vi를 안 채운 필드는 자동으로 `label`(한국어)로 폴백됨(정상 동작, 에러 아님). `tech_daily_report`의 `status`/`category`처럼 DB 값 자체를 언어별로 유지하는 게 아니라, "관리자가 직접 짓는 이름"이라 `I18N` 객체(고정 UI 문구용)로는 다국어 처리를 할 수 없어서 컬럼을 따로 둔 구조.
  - **입력창은 하나, 언어는 자동 감지(2026-08-31 수정)**: `/daily-fields`의 필드 등록/수정 폼은 "이름" 입력창 하나뿐이다 — 관리자가 한국어/영어/베트남어 중 아무 언어로나 입력하면 `worker.js`의 `detectTextLanguage()`가 문자 범위(한글 유무 → ko, 베트남어 전용 성조부호 유무 → vi, 그 외 → en)로 어떤 언어인지 판별하고, `resolveTrilingualLabel()`이 Workers AI 모델(`@cf/meta/m2m100-1.2b`, `wrangler.toml`의 `[ai]` 바인딩 `AI`)로 나머지 두 언어를 번역해서 `label`/`label_en`/`label_vi` 세 칸을 한 번에 채운다. 처음엔 "한국어 이름 필수 + 영어/베트남어 선택 입력"으로 만들었었는데, 사용자가 원한 건 "아무 언어로나 적어도 화면 언어에 맞춰 보이는 것"이라 이렇게 다시 고쳤음 — 이 종류의 요구사항은 지레짐작하지 말고 사용자 표현을 그대로 재확인할 것.
  - 수정 화면에서는 이름 입력창이 **관리자가 보고 있는 화면 언어의 이름으로 미리 채워짐**(`resolveFieldLabel(field, lang)`). 그 값을 안 바꾸고 그대로 다시 저장하면 재번역(AI 호출)을 건너뛴다 — `input_type`만 바꾸는 흔한 수정에서 매번 AI를 호출해 느려지는 걸 방지.
  - 성조부호를 생략한 베트남어도 업무 단어 조합으로 판별한다. 다만 한두 단어짜리 고유명사처럼 영어/베트남어를 문자만으로 구분할 수 없는 값은 원문을 유지하거나 관리자가 다시 저장해 번역 캐시를 갱신한다.
  - 이 저장 요청은 이름이 바뀐 경우 몇 초~십수 초 걸릴 수 있음(모델 추론 시간, 두 언어 동시 호출로 절반으로 줄여둠) — 자주 하는 일일 업데이트 입력이 아니라 어쩌다 한 번 하는 "필드 정의" 작업이라 감수 가능한 지연으로 판단함. AI 호출이 실패해도(네트워크 오류 등) 조용히 null 처리되어 한국어로 폴백될 뿐 저장 자체는 실패하지 않음.
- `tech_daily_field_option` — `input_type='select'`인 필드의 선택지 목록(값/순서). `/daily-fields/:id`에서 관리.
- **계층형(캐스케이딩) 드롭다운** (2026-08-30 추가): `tech_daily_field.depends_on_field_id`로 이 필드가 어떤 다른 select 필드에 "종속"되는지 지정할 수 있음. 종속된 필드의 선택지(`tech_daily_field_option`)에는 `parent_option_id`로 상위 필드의 어떤 선택지 아래에 속하는지 표시됨 — 예: "PART"를 고르면 "업무구분" 드롭다운이 그 PART에 속한 값만 보이는 식. 새 필드는 항상 가장 나중에 만들어지므로(=sort_order가 가장 큼) 상위 항목 후보는 항상 자신보다 먼저 존재하는 select 필드로 제한되어 순환 참조가 생기지 않음. 상위 필드의 input_type을 select가 아닌 것으로 바꾸면 그걸 상위로 삼던 필드들의 `depends_on_field_id`는 자동으로 NULL 처리됨(고아 참조 방지). 브라우저에서의 실제 필터링은 `CASCADING_SELECT_SCRIPT`(순수 JS, 프레임워크 없음)가 처리 — `<option data-parent="...">`와 `<select data-depends-on="...">` 속성을 보고 상위 select 값이 바뀔 때마다 하위 select의 선택지를 숨김/표시함.
- `tech_daily_update` — 항목(item)에 날짜별 업데이트를 추가할 때마다 생기는 "봉투" 역할만 함 (item_id/report_date/author_id). 실제 입력값은 아래 value 테이블에 들어감.
- `tech_daily_update_value` — `tech_daily_update` 1건 + `tech_daily_field` 1건 조합마다 실제 입력값 하나(EAV). 필드가 늘거나 줄어도 스키마 변경이 필요 없음.
  - **값 자동 번역(2026-09-01 추가, 2026-09-03 보완)**: 자유 텍스트는 `value/value_en/value_vi`에 저장 시 번역하고, 누락 번역은 표시 시 공용 캐시로 보완한다. 일반 select 값은 DB 호환성을 위해 원문을 세 칸에 복사하지만 화면에서는 `STANDARD_OPTION_LABELS` 또는 `tech_translation_cache`로 번역한다. 단, 라벨이 정확히 `상태`인 표준 필드는 `DAILY_STATUS_LABELS`의 영문 코드를 세 칸 모두에 저장하며 관리 화면에서 임의 선택지를 추가/삭제할 수 없다. **글자가 하나도 없는 값**("120", "118/2", "98.3%" 같은 수량/코드)은 번역하지 않는다. 실제로 순수 숫자를 번역기에 넣었을 때 한국어 "120명", 베트남어 "Chương 118/2"처럼 의미가 변하는 문제를 막기 위한 예외다.
  - **AI 번역 품질 — 필드 이름(짧은 전문용어)과 실제 문장 내용은 신뢰도가 다름**: `resolveTrilingualText()`(Workers AI `@cf/meta/m2m100-1.2b`)는 "높은 온도 검사 과정에서 2개의 샘플에서 작은 균열이 발견되었으며..." 같은 실제 문장은 정확하게 번역하지만, "진행중인 공정"/"파트넘버"/"비고" 같은 **2~5글자짜리 한국어 전문용어를 필드 이름으로 번역시키면 엉뚱한 결과가 나오는 걸 확인함**(예: "진행중인 공정"→영어 "The progressive justice.", "비고"→베트남어 "Bồ Tát"(불교 용어 "보살")). 그래서 `/daily-fields`에서 짧은 기술 용어 필드를 새로 만들 때는 자동번역 결과를 그대로 믿지 말고 반드시 `label_en`/`label_vi`를 관리자가 직접 열어서 확인/수정할 것.
- 최초 시드: `제품`/`업무구분`/`작업내용`/`진행중인 공정`/`파트넘버`/`랏넘버`/`수량`/`양품 수량`/`불량 수량`/`수율`/`진행률`/`상태`/`이슈·조치내용`/`다음 계획`/`비고` 15개가 한·영·베 라벨과 함께 기본으로 들어있음. `업무구분`은 평가/불량분석/이슈대응/설비점검 모니터링, `상태`는 위 6개 영문 코드를 표준 선택지로 사용함.
- **주의**: `pageDailyItems`(항목 목록)의 "최근 상태" 열은 라벨이 정확히 `'상태'`인 필드의 최신 값을 하드코딩해서 찾아 보여줌 — 관리자가 그 필드 라벨을 바꾸거나 삭제하면 이 열은 조용히 `-`로 빠짐(에러는 안 남).
- 입력 화면: `/daily-items`(목록+새 항목 등록), `/daily-items/:id`(상세+업데이트 추가+종료 토글). 설정 화면(관리자 전용): `/daily-fields`.
- `/daily-fields/:id`에서 select 필드의 선택지를 **CSV 파일 업로드 또는 붙여넣기로 일괄 추가** 가능(`POST /daily-fields/:id/options/import`). 진짜 `.xlsx` 바이너리 파싱은 지원하지 않음 — 빌드 없는 단일 파일 워커에 XLSX 파서를 넣는 건 배보다 배꼽이 커서, 화면 안내 문구로 "엑셀은 CSV로 저장 후 업로드"를 유도함. 한 줄에 값 하나, 쉼표가 있으면 첫 칸만 사용(따옴표로 감싼 필드 내 쉼표 같은 완전한 CSV 이스케이프는 처리 안 함), 기존 값과 중복되면 자동 skip.
- `/daily-reports`(조회 화면, 2026-09-02 임원 대시보드로 확장)는 방콕 시간 기준 전일 보고를 기본으로 열고 `tech_daily_report`(과거 엑셀 아카이브)와 `tech_daily_item`+`tech_daily_update`+`tech_daily_update_value`(신규 입력)를 함께 읽는다. 상단에는 보고 건수/완료/이슈·지연/가중 수율/작성률 KPI, 전일 대비 변화, 자동 요약, 즉시 확인할 이슈, 미작성 활성 항목을 보여주고, 아래에는 SSD/Module별 표준 열(업무구분·제품·작업·공정·Part No·Lot No·수량·양품·불량·수율·진행상태·이슈/조치·담당자)로 정규화해 표시한다. 우측 상단 "인쇄 / PDF 저장" 버튼(`window.print()`)과 A4 가로 `@media print` CSS로 사이드바/필터폼/버튼류를 감추고 임원 보고 내용만 인쇄됨. 화면 상단에는 종료되지 않았는데 `STALE_THRESHOLD_DAYS`(3일) 넘게 업데이트가 없는 "정체 항목"도 날짜 필터와 무관하게 항상 보여줌.

### `tech_daily_report` (2026-08-30 추가, 과거 엑셀 아카이브 전용 — read-only, 2026-09-03부터 빈 테이블)

**2026-09-03: 사용자 요청으로 전체 1258행을 삭제함** — 실제 SSD/Module 최신 데이터가 `tech_daily_item`/`tech_daily_update*`(EAV)로 들어오면서 이 아카이브 테이블은 더 이상 쓰지 않기로 함(위 "2026-09-03 예시·과거 아카이브를 실제 SSD/Module 데이터로 교체" 참고). 테이블/코드(`/daily-reports`의 아카이브 조회 로직)는 아직 스키마·worker.js에 남아있으니 완전히 정리하려면 관련 렌더링 코드도 같이 걷어낼 것 — 지금은 "빈 테이블이라 그 구획이 화면에 아무것도 안 보이는" 상태로만 둠. 아래는 이 테이블이 살아있던 동안의 이력 기록.

SSD / Module 파트가 엑셀로 작성하던 일일업무보고를 옮겨 담았던 테이블. 컬럼은
`report_date, part('SSD'|'Module'), category, seq, title, content, progress_note, status, owner, remark`.

- **`status`와 `category`에는 CHECK 제약을 걸지 않았음.** `tech_task`와 달리 두 파트의 상태값 체계가 완전히 다르고(SSD는 `ING`/`Done`/`Waitting`, Module은 `STEP3`/`입력대기`/`진행 중`/`결과 송부` 등 수십 종), 시트에 따라 한국어·베트남어 원문이 섞여 있어 고정 목록으로 묶을 수 없음. 화면에 표시할 때 번역이 필요하면 매핑 테이블을 따로 두고, DB 값은 원문 그대로 유지할 것.
- **`title`, `category`가 비어 있는 행이 많음(각각 447/38행)** — 원본 엑셀의 병합 셀 때문이며 정상. NOT NULL을 걸지 말 것.
- SSD 시트에는 `remark`가, Module 시트에는 `seq`/`progress_note`/`owner`가 원래 없어서 해당 파트 행에서는 NULL.
- 2026-08 데이터 1258행 적재 완료 (Module 930행/23일치, SSD 328행/7일치 — SSD는 원본이 8/21부터만 존재). 원본 8/29 시트와 대조하여 행 수·본문 일치 확인함.
- **재임포트 시 중복 주의** — 유니크 제약이 없으므로 같은 파일을 다시 넣으면 그대로 중복 적재됨. 특정 날짜를 다시 넣을 때는 `DELETE FROM tech_daily_report WHERE report_date = ? AND part = ?` 후 INSERT 할 것.
